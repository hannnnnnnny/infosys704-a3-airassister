1. 业务判断与优先顺序
继续采用 A2 的直订机票退款准备与分流方案。V1.1 已有真实本地申请、资料不足、标准/专家路由、队列归属、重开、版本保护和事件历史；38 项后端测试及真实浏览器验收有证据。本次不扩大到退款决定、真实航空订票或支付。
首要业务成果是一条完整、可解释的案件准备闭环：提交→识别未完成证据→人工检查→有理由的标准/专家交接→乘客查询与回执一致。查询/草稿控制是确保这条闭环可靠的支撑；SAP财务参考则补充有说明、来源和时间的上下文，不是新增装饰性模块或未经验证的AI资格判断。优先完成已有范围，不以复杂度代替方案质量。
非 PPT 评分关注合计150分：理由10、设计30、功能60、易用50；并非剩余150分已经获得，也不免除正式A3的后续交付要求。改进是否增加分数仍由评分者判断。

2. 案件准备闭环、责任和可测成功条件
本次闭环的终点是“证据状态清楚、有理由地交给负责角色，并让查看者取到同一份已存记录”，而不是“已退款”。更大的业务退款闭环还包括资格/金额决定、授权、付款指令核对及银行到账；这些不在本原型能力内。需要在Option2中分别说明已实施机制、合成替代和真实接入缺口。

3. P0 — 查询竞态与审核草稿保护
交付目的：迟到查询不能覆盖后来的案件或错误状态，切换视图不能无声丢掉正在编辑的审核内容。
查询应绑定明确的查询意图、视图和 owner reference/email。用户发起新的查询、清空或切换案件时，旧请求的成功/失败回调都应失效；可使用取消机制，但取消本身不能替代响应归属检查。Save/Handoff/Reopen 的响应也应只更新对应的当前案件。
审核草稿以案件和版本为边界保存最少必要的原型字段。采用明确的未保存提示、继续编辑/放弃入口或安全的临时恢复方式。草稿不是已提交审核，不得提前改变乘客进度、队列或事件。不同案件/联系邮箱不得共享草稿；不把 SAP key、真实个人资料或服务配置放入浏览器草稿。
收到版本冲突时，保留用户本次编辑，展示新版本和冲突原因，要求人工复核后重试；不得自动重放旧修改覆盖新结果。Queued 状态仍须带备注 Reopen 后再修改，Handoff 不得绕过尚未保存的检查变化。

P0 验收
A01：连续查 A→B，让 A 后返回，结果仍为 B；旧失败也不覆盖新的成功。
A02：正确 owner→错误 owner，迟到的正确结果不会重新显露旧案件；恢复正确 owner 后可重新查询。
A03：编辑检查/reference/note 后切换页面/案件，按设计明确保留或请求放弃；恢复的是对应案件的未保存草稿，并清楚标注。
A04：未保存草稿不写数据库、不追加事件、不改变乘客状态；保存成功后草稿转为对应已存版本。
A05：两次保存使用同一旧版本，只有一次可成功；另一次冲突不丢草稿、不自动覆盖。实际多浏览器/异步验证与隔离测试分别记录，不能用后端测试假称全部UI已验收。
A06：使用键盘可到达查询、草稿操作、保存/重开等关键控件；只记录实际检查的路径。

4. P1 — 案件上下文中的只读 SAP 财务快照
交付目的：从“独立查到一个泛化财务文档”提升到“这个本地案件为何引用该财务记录、引用的是什么版本/时间/来源”的可追溯参考。
使用已获准的个人 SAP API Hub sandbox 只读 GET。客户端提交文档ID及人工引用说明；服务端通过已有 SAP adapter 获取、验证、规范化真实返回，不能接受浏览器自称 Live 的金额/状态对象作为财务证据。
保存快照至少包括 documentID、服务端返回的财务字段、币种、原始流程/审批字段、referenceDocument、createdAt（如提供）、来源模式/标签、fetchedAt、案件版本、引用说明和本地事件。未知字段保持未知。快照是某次读取结果；再次读取应明确是新获取时间或新快照，不能让历史记录悄悄变成最新值。
引用说明表达人工选择该记录的理由，不是系统验证过的机票/付款匹配。可使用明确的 synthetic demonstration 说明，不制造真实客户关联。不要把通用 SAP 文档 net amount 填进机票 paid fare、申请 approved amount 或 refunded amount。原始process C、category H或空审批值不得映射为真实付款/批准结论。
添加快照是本地案件修改，应使用当前 owner pair 和版本控制，并遵守 queued→reopen 的已有编辑边界。成功保存才能追加事件；失败、404、超时或版本冲突不能留下假记录、假事件或不一致版本。读取/添加快照不改变 deterministic route、eligibility、approval、amount或payment。
无凭据的交付包应显示未配置/无法读取，不以固定 SAP 样例冒充 Live。此前个人 sandbox HTTP200证明接口可读，不证明任意文档可读、POST权限、个人S/4HANA生产租户或实际航空业务数据。

P1 验收
A07：实际个人 GET 已知文档返回真实字段，保存后 reload/restart、reviewer、Track/receipt（若展示）均返回同一已存快照、说明、版本和事件；源模式/时间保持可见。
A08：不存在/未配置/上游失败/缺字段时展示真实状态；无假金额、无例子替代Live、无新增成功事件。上游故障的mock测试和实际接口结果必须分开。
A09：客户端伪造 financial fields/source/fetch time 被拒绝或不被作为服务端证据采用；错误 owner、不合法payload、旧版本不能保存。
A10：queued案件不可直接改变快照，按模型先重开；两个旧版本并发更新不产生丢失写入或两个成功事件。
A11：加入快照后，本地queue/route仍为原规则结果；refund eligibility/amount/approval/payment仍未确定，sapCreditMemoRequestId不得因此伪装为本地申请已在SAP创建。
A12：actual SAP key不在HTML/JS、快照、事件、下载、OpenCode输入或ZIP中；课堂临时身份不用于项目接入。

5. P1 的业务适配结论：加强Option2，但有明确剩余边界
A2 V8 ¶7/67/69/79-81要求授权内部记录、未解决信息、标准/复杂路由、责任归属和人工决定。持久化财务参考及说明会加强“可见案件上下文和财务参考追溯”的部分适配，避免SAP成为完全旁置的演示页。
它仍不能替代授权航空公司 booking/ticket/payment/disruption 的检索与对账。手动引用的generic SAP sandbox document不是自动验证的booking match。不能把新增快照说成原A2三部分全部实现；Option2的改动说明必须继续列出synthetic数据、manual prototype checks、local queues/events和read-only金融参考。若评分者认为API与原方案完全不适配，Option3边界仍需按正式规则判断，不能靠修改文件措辞消除这个实质差距。

6. P2 — 保持可解释的prototype路由，完善150分范围的论证
继续采用 deterministic prototype-v1 route 和明示理由，不增加无法验证的AI自动审批。输入/checks、supported reason、specialist flag和缺项决定本地准备/分流，人的eligibility/amount/approval/payment责任不变。规则是可演示的原型规则，不是Air New Zealand政策。
